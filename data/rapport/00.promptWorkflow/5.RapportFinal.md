

# PROMPT GÉNÉRIQUE — Rapport final de phase

## Contexte

Tu interviens sur le projet `Toolkit-Bridge`.

Nous sommes à la fin de la phase suivante :

```text
{PHASE_PATH}
```

Nom de la phase :

```text
{PHASE_NAME}
```

Cette phase est considérée comme terminée fonctionnellement.

Tu dois produire le rapport final de phase conformément au workflow projet.

Le workflow de référence impose qu’un rapport final documente :

* ce qui a été implémenté ;
* ce qui n’a pas été fait ;
* les dettes techniques assumées ;
* les décisions structurantes ;
* les impacts ;
* les recommandations futures.

## Fichiers à analyser

Analyser tous les fichiers disponibles dans :

```text
{PHASE_PATH}
```

Inclure notamment :

* les prompts d’analyse ;
* les rapports d’analyse ;
* les prompts d’implémentation ;
* les rapports d’implémentation ;
* les rapports de review ;
* les prompts de correction ;
* les rapports de correction ;
* les éventuelles documentations produites.

Si certains fichiers attendus sont absents, le signaler explicitement sans inventer leur contenu.

## Objectif

Créer un rapport final permettant de comprendre :

* l’objectif initial de la phase ;
* ce qui a réellement été livré ;
* les écarts par rapport à la roadmap ;
* les décisions prises ;
* les corrections réalisées ;
* les limites restantes ;
* les impacts sur la suite ;
* les recommandations futures.

## Structure attendue

Créer le fichier :

```text
{PHASE_PATH}/z_finalRepport.md
```

Le rapport doit contenir les sections suivantes.

---

## 1. Résumé exécutif

Présenter :

* objectif de la phase ;
* résultat final ;
* statut : terminée / partiellement terminée / non terminée ;
* niveau de maturité atteint ;
* conclusion courte.

---

## 2. Périmètre initial

Rappeler ce que la phase devait couvrir d’après la roadmap ou les prompts initiaux.

Indiquer si le périmètre a évolué en cours de route.

---

## 3. Synthèse des étapes / lots

Pour chaque étape ou lot trouvé dans la phase :

* objectif ;
* analyse réalisée ;
* implémentation réalisée ;
* corrections réalisées ;
* état final ;
* fichiers principaux modifiés ou créés ;
* tests exécutés ;
* points de vigilance.

Ne pas inventer les lots absents.

---

## 4. Ce qui a été implémenté

Lister précisément les capacités livrées.

Regrouper par domaine si pertinent :

* runtime ;
* orchestration ;
* validation ;
* Telegram ;
* WebUI ;
* configuration ;
* sécurité ;
* erreurs ;
* tests ;
* documentation.

---

## 5. Ce qui n’a pas été fait

Lister les éléments volontairement hors scope ou reportés.

Distinguer :

* volontairement reporté ;
* non traité faute de besoin ;
* manquant réel ;
* à reconsidérer plus tard.

---

## 6. Décisions structurantes

Lister les décisions importantes prises pendant la phase.

Pour chaque décision :

* expliquer la décision ;
* expliquer pourquoi elle a été prise ;
* indiquer si elle doit être conservée, documentée, ou revisitée.

---

## 7. Corrections et stabilisations réalisées

Lister les corrections importantes issues des reviews :

* bugs corrigés ;
* dérives évitées ;
* dette structurelle corrigée ;
* sécurité renforcée ;
* tests ajoutés.

---

## 8. Impacts techniques

Analyser les impacts sur :

* architecture ;
* maintenabilité ;
* exploitation ;
* sécurité ;
* tests ;
* futures phases.

---

## 9. Dettes techniques assumées

Lister les dettes restantes.

Pour chaque dette :

* description ;
* gravité ;
* pourquoi elle est acceptable maintenant ;
* où la reprendre plus tard.

---

## 10. Dérives utiles et adaptations

Identifier les écarts par rapport au plan initial.

Pour chaque dérive :

* saine / risquée / à surveiller ;
* justification ;
* impact sur la suite.

---

## 11. Tests et validation

Résumer :

* tests ajoutés ;
* tests exécutés ;
* résultats ;
* limites de couverture restantes.

---

## 12. Documentation produite

Lister les documents créés ou mis à jour.

Indiquer s’il manque une documentation utilisateur, technique ou d’exploitation.

---

## 13. Recommandations futures

Classer les recommandations :

### À court terme

### À moyen terme

### À long terme

Ne pas transformer cette section en roadmap complète.

---

## 14. Conclusion

Conclure clairement :

* phase clôturable ou non ;
* valeur produite ;
* risques restants ;
* prochaine étape recommandée.

## Contraintes strictes

* Ne pas modifier le code.
* Ne pas modifier les roadmaps.
* Ne pas inventer de fichiers.
* Ne pas inventer de fonctionnalités.
* Si une information manque, le dire explicitement.
* Garder un ton factuel.
* Ne pas masquer les dettes.
* Ne pas transformer le rapport final en nouvelle roadmap.

## Résultat attendu

Créer :

```text
{PHASE_PATH}/z_finalRepport.md
```

Le rapport doit être suffisamment complet pour servir de base aux phases suivantes et aux analyses globales.
