# PROMPT — Analyse Phase 9 Logging Étape 1 — Ajouter une journalisation intelligente à CodexTime

## Contexte

Tu interviens sur `Toolkit-Bridge`, sous-système `CodexTime`.

Depuis les premières phases de CodexTime, beaucoup de composants ont été ajoutés :

* runtime workflow ;
* steps Codex ;
* runner ;
* validation Maven ;
* auto-correction ;
* CLI ;
* Telegram workflow ;
* registre projet ;
* résolution `projectName → projectPath` ;
* injection `codexWorkingDirectory` ;
* appel `codex exec --cd ... -`.

Mais la plupart des classes ajoutées manquent de logs applicatifs.

L’objectif n’est pas d’ajouter des logs partout, mais de rendre le workflow exploitable et debuggable.

## Objectif de l’analyse

Identifier où ajouter une journalisation utile, sobre et structurée.

Les logs doivent permettre de comprendre :

* quand un workflow démarre ;
* quel projet / phase / étape est concerné ;
* quand Codex est appelé ;
* quand une validation Maven démarre / échoue / réussit ;
* quand le workflow passe en `WAIT_HUMAN` ;
* quand une reprise est lancée ;
* quand une commande Telegram importante est utilisée ;
* quand une erreur est réellement soulevée.

## Exigence technique

Utiliser Lombok :

```java
@Slf4j
```

sur les classes concernées.

Ne pas utiliser :

```java
LoggerFactory.getLogger(...)
```

sauf si le projet l’utilise déjà fortement dans la zone concernée.

## 2. Définir une stratégie de niveaux de log

Proposer une stratégie simple :

### INFO

À utiliser pour les événements métier importants :

* démarrage d’un workflow ;
* démarrage d’un resume ;
* fin de workflow ;
* passage en `WAIT_HUMAN` ;
* échec final ;
* validation Maven lancée / terminée ;
* appel Codex lancé / terminé ;
* projet enregistré ou mis à jour ;
* roadmap chargée.

### DEBUG

À utiliser pour les détails utiles au diagnostic :

* résolution de projectName ;
* phase/etape ciblées ;
* construction du contexte ;
* chemins internes uniquement si c’est acceptable en DEBUG ;
* décision retournée par un step ;
* durée d’exécution ;
* code retour processus ;
* nombre de caractères stdout/stderr ;
* nombre de chunks summary envoyés.

### WARN

À utiliser pour les situations anormales mais récupérables :

* projet inconnu ;
* roadmap absente ;
* summary absent ;
* tentative de run alors qu’un run est déjà en cours ;
* whitelist vide déjà gérée ailleurs si concerné ;
* path projet refusé ;
* validation Maven échouée mais correction possible ;
* quota/rate-limit détecté.

### ERROR

À utiliser au moment où une erreur est réellement soulevée ou provoque un échec :

* exception Codex CLI ;
* exception Maven/process ;
* timeout process ;
* exception runner ;
* erreur non récupérable ;
* `STOP_FAILURE` final si associé à une cause technique.

## 3. Définir les champs utiles à logger

Proposer une liste de champs à utiliser de manière cohérente :

* `runId`
* `chatId`
* `userId`
* `botId`
* `projectName`
* `phase`
* `etape`
* `decision`
* `status`
* `durationMs`
* `exitCode`
* `artifactType`
* `artifactPath` uniquement en DEBUG si acceptable
* `command` uniquement sans secret
* `provider`
* `model`

Ne jamais logger :

* token Telegram ;
* clé API ;
* secret ;
* prompt complet Codex ;
* contenu complet des rapports ;
* contenu complet du summary ;
* path absolu en INFO si ce n’est pas nécessaire.

## 4. Identifier précisément où ajouter des logs

Pour chaque classe pertinente, proposer :

* les méthodes à logger ;
* le niveau ;
* le message exact ou le pattern recommandé ;
* les champs à inclure ;
* ce qu’il ne faut pas logger.

Exemples attendus :

```java
log.info("Starting workflow run: runId={}, chatId={}, project={}, phase={}, etape={}",
        runId, chatId, projectName, phase, etape);
```

```java
log.debug("Workflow context built: runId={}, variables={}",
        runId, variables.keySet());
```

```java
log.warn("Workflow run rejected: chatId={}, reason={}", chatId, reason);
```

```java
log.error("Codex execution failed: command={}, exitCode={}, durationMs={}",
        safeCommand, exitCode, durationMs);
```

## 5. Vérifier la politique de confidentialité des logs

Analyser les risques :

* fuite de chemins absolus ;
* fuite de prompts ;
* fuite de summary ;
* fuite de tokens ;
* stacktrace trop verbeuse ;
* logs Telegram trop bavards.

Proposer des règles :

* INFO = pas de path absolu sauf nécessité forte ;
* DEBUG = path possible si utile, mais jamais secrets ;
* ERROR = stacktrace OK côté serveur, pas côté Telegram ;
* jamais le prompt complet ;
* jamais les tokens.

## 6. Préparer l’implémentation

Proposer un plan d’implémentation en 5 à 8 étapes maximum.

Le plan doit être progressif, par exemple :

1. logs orchestration Telegram ;
2. logs runner/orchestrator ;
3. logs Codex client ;
4. logs validation Maven/process ;
5. logs registry projet / roadmap / summary ;
6. tests ou vérifications non-régression.

## 7. Tests et vérifications

Proposer ce qui doit être testé ou vérifié :

* compilation avec `@Slf4j` ;
* absence de logging de tokens ;
* absence de prompt complet dans les logs ;
* pas d’impact sur les tests existants ;
* éventuellement test unitaire sur utilitaire de sanitization si ajouté.

Ne pas écrire de tests fragiles qui assertent tous les messages de logs.

## Contraintes strictes

* Ne rien implémenter dans cette analyse.
* Ne pas ajouter des logs partout mécaniquement.
* Ne pas logger les prompts complets.
* Ne pas logger les tokens.
* Ne pas logger les contenus complets de fichiers.
* Ne pas transformer les logs en UX utilisateur.
* Ne pas modifier le comportement métier.
* Ne pas ajouter de framework de logging.
* Utiliser `@Slf4j`.
* Rester sobre.
