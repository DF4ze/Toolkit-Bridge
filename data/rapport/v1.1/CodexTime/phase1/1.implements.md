Points de cadrage complémentaires à respecter absolument :

## 1. Simplicité stricte

Je veux un socle runtime minimal, pas un framework de workflow.
Donc :

* pas de moteur de transitions
* pas de DSL
* pas de plugin system
* pas de service runtime
* pas de logique de navigation complexe entre lots

## 2. `WorkflowRun`

Le modèle doit rester simple.
Je veux au minimum :

* un identifiant de run
* un nom ou type de workflow
* une référence d’étape cible simple
* un statut global
* une liste de lots
* un pointeur simple vers le lot courant
* timestamps utiles
* éventuellement une map simple de contexte global si cela reste très sobre

Important :

* le pointeur de lot courant doit rester **très simple**
* un identifiant de lot courant ou un index courant suffit
* ne pas introduire de logique de navigation avancée

## 3. `LotRun`

Je veux un modèle simple représentant un lot en cours d’exécution.
Au minimum :

* identifiant
* code/nom de lot
* ordre d’exécution
* statut
* compteur de tentatives de correction
* références/chemins d’artefacts
* timestamps utiles
* éventuellement un résumé simple

Important :

* `LotRun` ne doit pas devenir un doublon de `Task`
* il représente un état de workflow, pas une task générique du système

## 4. `WorkflowExecutionContext`

Je valide le principe, mais attention :

* ce contexte doit rester un **transport technique**
* il ne doit pas devenir un conteneur fourre-tout

Donc :

* il peut contenir `WorkflowRun`
* il peut contenir `LotRun`
* il peut contenir une map de variables/contexte
* mais cette map doit rester sobre et explicitement pensée comme contexte technique transitoire

Pas de dérive vers un moteur de scripting ou de résolution dynamique.
