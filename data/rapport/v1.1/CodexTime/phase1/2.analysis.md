Tu travailles sur le projet Toolkit-Bridge.

Objectif du lot :
introduire le contrat minimal des étapes de workflow, sans implémenter de moteur de workflow ni d’orchestrator.

Contexte :
le lot précédent a introduit le modèle runtime minimal :

* `WorkflowRun`
* `LotRun`
* `WorkflowExecutionContext`
* les enums de statuts

Nous voulons maintenant poser la base permettant de définir des étapes de workflow, sans encore implémenter le workflow complet.

---

## Objectif précis

Créer :

1. une interface `WorkflowStep`
2. un objet résultat `WorkflowStepResult`
3. une enum de décision associée

Ces éléments doivent permettre à terme :

* d’exécuter une étape
* de savoir quoi faire ensuite (continuer, corriger, bloquer, etc.)
* sans introduire de logique d’orchestration ici

---

## Contraintes importantes

* pas de moteur de workflow
* pas d’orchestrator
* pas de gestion de séquence d’étapes
* pas de pipeline
* pas de plugin system
* pas de DSL
* pas de dépendance à Telegram, Codex, Maven
* rester strictement dans un contrat minimal

👉 On pose uniquement une API, pas un système complet

---

## 1. Interface `WorkflowStep`

Créer une interface simple du type :

* méthode principale :

    * prend un `WorkflowExecutionContext`
    * retourne un `WorkflowStepResult`

Exemple attendu (conceptuellement) :

* `execute(context) -> result`

Contraintes :

* pas de logique par défaut complexe
* pas d’état interne
* pas de dépendance externe

---

## 2. `WorkflowStepResult`

Créer un objet représentant le résultat d’une étape.

Il doit permettre de représenter :

* la décision à prendre
* un message ou résumé
* éventuellement des données complémentaires utiles à la suite

Champs attendus (minimum) :

* `decision`
* `message` (optionnel mais recommandé)
* éventuellement un objet ou map de données simples

Important :

* rester simple
* pas de structure trop riche
* pas de logique métier

---

## 3. Enum de décision

Créer une enum simple (ex: `WorkflowStepDecision`) avec les valeurs suivantes :

* CONTINUE
* RETRY_CORRECTION
* WAIT_HUMAN
* STOP_FAILURE
* FINISH

Tu peux adapter légèrement les noms si nécessaire, mais reste très proche.

---

## 4. Placement des classes

Respecter la cohérence avec le lot précédent :

* package recommandé :
  `fr.ses10doigts.toolkitbridge.service.agent.workflow.runtime`

ou
`fr.ses10doigts.toolkitbridge.service.agent.workflow.runtime.step`

👉 à toi de proposer le meilleur placement cohérent avec le projet

---

## 5. Style attendu

* simplicité maximale
* cohérence avec le projet
* pas de sur-conception
* pas de pattern complexe
* validations minimales si nécessaire
* pas de logique cachée

---

## 6. Tests

Tu peux ajouter uniquement le strict minimum :

* création d’un `WorkflowStepResult`
* vérification des valeurs
* éventuellement un test simple d’une implémentation dummy de `WorkflowStep`

Pas de tests complexes.

---

## 7. Ce que je ne veux pas dans ce lot

* pas de `WorkflowRunner`
* pas d’orchestrator
* pas de gestion de liste d’étapes
* pas de gestion de transition entre étapes
* pas de logique de retry
* pas de logique métier
* pas de lien avec Codex
* pas de parsing de roadmap
* pas d’implémentation concrète de step métier
