## Objectif de l'analyse

Analyser comment introduire une amélioration simple et utile de l'observabilité du workflow pour :
- `WAIT_HUMAN`
- `STOP_FAILURE`
- reprise manuelle
- correction déclenchée ou non

Ce n'est PAS le moment d'intégrer Telegram, un système événementiel, un dashboard, une persistance avancée, ni une nouvelle architecture lourde.

## Points à analyser explicitement

A. Forme d'observabilité recommandée :
1) enrichir `WorkflowStepResult.message/data`
2) générer un artefact récapitulatif dédié
3) combiner les deux simplement

B. Portée minimale visible : décision finale, raison d'arrêt, correction déclenchée ou non, chemins d'artefacts utiles.

C. Emplacement de la logique : orchestrator / runner / steps / brique dédiée.

D. Rapport aux artefacts existants : suffisant ou ajout d'un "workflow summary" simple.

E. Exploitabilité locale de `WAIT_HUMAN` : message clair, résumé dédié, chemin à éditer, raison courte.

F. Reprise manuelle : expliciter quoi éditer, quoi relancer, comment savoir que la reprise est prête.

G. Contexte runtime :
1) suffit tel quel
2) le modifier maintenant
3) suffit avec conventions simples

H. Préparation future de l'intégration Telegram sans implémentation : stabiliser messages, normaliser champs, centraliser un résumé.

I. Exclusions de périmètre : Telegram, API REST, dashboard web, système d'événements, persistance avancée, observabilité distribuée, métriques complexes, moteur de notification.

Le but est de rendre le système plus lisible, pas de construire une couche de reporting.
