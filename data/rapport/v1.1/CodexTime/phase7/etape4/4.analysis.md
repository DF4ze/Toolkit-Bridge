# PROMPT — Analyse Phase 7 Étape 4 — Gestion WAIT_HUMAN / Resume

## Contexte

Le système actuel permet :
* `/workflow_run` → lance un workflow
* `/workflow_status` → consulter l’état
* `/workflow_summary` → lire le summary

Le workflow peut produire un état :

```text
WAIT_HUMAN
```

Ce cas correspond à :
* une décision humaine requise
* une modification manuelle d’un fichier (ex: review)
* ou une validation avant reprise

Le runner supporte déjà une reprise via :

```text
mode=RESUME
```

## Objectif

Permettre depuis Telegram :

```text
WAIT_HUMAN → utilisateur agit → /workflow_resume → reprise
```

Sans casser :
* le runner
* la CLI
* le contrat existant

## Travail demandé

## 1. Quand considérer qu’un resume est possible ?

Analyser :
* `WorkflowTelegramSession.lastStatus`
* cas valide :

```text
WAITING_HUMAN
```

* cas invalides :

```text
RUNNING
FAILED
IDLE
````

## 2. Où stocker les infos nécessaires au resume ?

Identifier les éléments déjà présents :
* projectName
* phase
* etape
* roadmapPath
* lastSummaryPath

Identifier ce qui manque potentiellement :
* chemin du fichier à modifier (ex: reviewResultPath)
* paramètres CLI de reprise
* état de correction (optionnel)

## 3. Comment appeler le resume ?

Comparer :

### Option A — CLI

```text
AnalysisReviewWorkflowCli --mode=RESUME
```

### Option B — appel Java direct (recommandé)

```java
runner.runAnalysisReviewWithOptionalCorrection(...)
```

## 4. Différence RUN vs RESUME

Clarifier :
* RUN → part d’un état initial
* RESUME → part d’un état intermédiaire

Identifier :
* quels paramètres changent
* quels fichiers doivent exister
* quelles erreurs possibles

## 5. Commande Telegram

Ajouter :

```text
/workflow_resume
```

Analyse attendue :
