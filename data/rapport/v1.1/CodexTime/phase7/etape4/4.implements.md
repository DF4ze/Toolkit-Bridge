# PROMPT — Implémentation Phase 7 Étape 4 — WAIT_HUMAN / Resume Telegram

## Contexte

Le système Telegram permet déjà :
* `/workflow_run`
* `/workflow_status`
* `/workflow_summary`

Le workflow peut terminer en :

```text
WAIT_HUMAN
```

Dans ce cas, la session Telegram est mise à jour avec :

```text
lastStatus = WAITING_HUMAN
running = false
```

L’objectif de cette étape est d’ajouter une reprise contrôlée depuis Telegram.

## Objectif

Ajouter la commande :

```text
/workflow_resume
```

Elle doit reprendre un workflow uniquement si la session courante est en attente humaine.

## Travail demandé

### 1. Ajouter la commande Telegram

Dans `WorkflowTelegramController`, ajouter :

```java
@Command("/workflow_resume")
```

Le controller doit rester fin :
* récupérer `chatId`
* déléguer à `WorkflowTelegramOrchestrationService`
* retourner le message utilisateur

### 2. Ajouter une méthode resume dans l’orchestration

Dans `WorkflowTelegramOrchestrationService`, ajouter une méthode du type :

```java
resume(chatId, userId)
```

Comportement attendu :
1. récupérer la session
2. vérifier :
   * `lastStatus == WAITING_HUMAN`
   * `running == false`
   * `phase != null`
   * `etape != null`
3. si invalide :
   * retourner un message clair
   * ne rien lancer
4. générer un `runId`
5. appeler `tryMarkRunning(chatId, runId)`
6. lancer l’exécution async

### 3. Appel runner

Pour le resume, appeler :

```java
runner.runCorrectionAfterReview(context)
```

Ne pas utiliser :
* `runAnalysisReviewWithOptionalCorrection`
* la CLI
* `ProcessBuilder`

### 4. Construire le contexte RESUME

Le contexte doit contenir :
* `reportRootDirectory`
* `reportVersion`
* `reportPhase`
* `stepNumber`

Il ne doit pas contenir `analysisSourcePath`, car ce champ est spécifique au RUN.

### 5. Mapping résultat

Réutiliser la logique existante si possible :
* `WAIT_HUMAN` → session `WAITING_HUMAN`
* `CONTINUE` (ou succès équivalent) → session `COMPLETED`
* `STOP_FAILURE` → session `FAILED`
* exception → session `FAILED`

### 6. Gestion du lock

Réutiliser :

```java
tryMarkRunning(chatId, runId)
```

Si un run est déjà en cours :

```text
❌ Workflow already running
```

### 7. Règle importante sur `phase/etape`

Ne pas incrémenter `etape` dans cette étape.

En particulier :

```text
WAITING_HUMAN conserve phase/etape de l’étape suspendue.
```

### 8. UX messages

Succès immédiat :

```text
🚀 Resume lancé
```

Refus :

```text
❌ Aucun workflow en attente d'action humaine
```

Contexte incomplet :

```text
❌ Contexte workflow incomplet
```

### 9. Tests attendus

Ajouter tests unitaires :
* resume accepté quand session `WAITING_HUMAN`
* resume refusé si `IDLE`
* resume refusé si `FAILED`
* resume refusé si `COMPLETED`
* resume refusé si `RUNNING`
* resume refusé si `phase` ou `etape` manquant
* double resume refusé via `tryMarkRunning`
* résultat `CONTINUE` → session `COMPLETED`
* résultat `WAIT_HUMAN` → session `WAITING_HUMAN`
* résultat `STOP_FAILURE` → session `FAILED`

### 10. Contraintes strictes

* ne pas modifier le runner
* ne pas modifier la CLI
* ne pas modifier l’orchestrateur
* ne pas parser le summary
* ne pas ajouter de DB
* ne pas incrémenter automatiquement l’étape
* ne pas passer automatiquement à la phase suivante
