# PROMPT — Analyse Phase 7 Étape 6 — Sécurité minimale Telegram

## Contexte

Tu interviens sur le projet `Toolkit-Bridge`.

La Phase 7 vise l’intégration Telegram du workflow Codex.

Les étapes précédentes permettent maintenant :

* `/workflow` : tableau de bord workflow
* `/workflow_run` : lancer un workflow
* `/workflow_status` : consulter l’état
* `/workflow_summary` : consulter le summary
* `/workflow_resume` : reprendre après `WAITING_HUMAN`
* `/workflow_roadmap_load` : charger une roadmap

Le module Telegram dispose déjà d’un mécanisme de sécurité par bot avec whitelist `allowed-user-ids`.

## Objectif

Analyser la sécurité minimale à garantir pour éviter qu’un utilisateur non autorisé puisse piloter le workflow depuis Telegram.

L’objectif n’est pas d’ajouter une sécurité complexe, mais de vérifier et renforcer si nécessaire :

* la whitelist Telegram existante ;
* l’isolation du bot `Cortex` ;
* les commandes workflow sensibles ;
* les messages de rejet ;
* l’absence de fuite d’informations sensibles.

## Travail demandé

### 1. État actuel de la sécurité Telegram

Analyser :

* configuration `telegram.bots[].security.allowed-user-ids`
* comportement si whitelist vide
* comportement si utilisateur non autorisé
* fonctionnement de `/start` pour récupérer son identifiant Telegram
* interaction avec `@TelegramController(bot = "Cortex")`

### 2. Commandes sensibles

Identifier les commandes sensibles :

* `/workflow_run`
* `/workflow_resume`
* `/workflow_summary`
* `/workflow_roadmap_load`
* `/workflow_status`
* `/workflow`

Classer le niveau de risque pour chacune.

### 3. Suffisance de la whitelist existante

Répondre clairement :

* est-ce que la whitelist existante protège déjà toutes les commandes workflow ?
* faut-il ajouter une vérification supplémentaire côté controller/service ?
* faut-il éviter la double sécurité ?

### 4. Configuration à vérifier

Identifier les propriétés nécessaires :

* bot `Cortex` déclaré
* token présent
* whitelist non vide recommandée
* polling enabled
* auto-register commands éventuel

### 5. Fuite d’informations

Vérifier que les messages Telegram ne renvoient pas inutilement :

* tokens
* chemins absolus
* stack traces
* erreurs techniques trop détaillées
* contenu de fichiers non autorisés

### 6. Sécurité des chemins

Analyser la sécurité déjà en place pour :

* `roadmap load`
* `workflow_summary`
* workspace/shared
* reportRootDirectory

Vérifier qu’il n’y a pas de contournement évident.

### 7. Sécurité du run async

Analyser :

* double run
* runId
* timeout
* race condition
* session par chatId
* risque d’un utilisateur autorisé dans un groupe

### 8. Recommandations minimales

Classer :

#### À faire maintenant

Petites corrections indispensables.

#### À documenter seulement

Points déjà couverts par le module Telegram.

#### À reporter

Sécurité avancée, rôles, multi-user, audit, DB.

### 9. Tests à prévoir

Proposer des tests utiles :

* utilisateur non autorisé rejeté par le module ?
* controller non appelé si non autorisé ?
* whitelist vide = comportement attendu ?
* messages ne contiennent pas de path absolu ?
* commandes sensibles non accessibles sans whitelist ?

### 10. Plan d’implémentation

Proposer un plan en 5 à 10 étapes maximum si des corrections sont nécessaires.

## Contraintes strictes

* Ne rien implémenter.
* Ne pas modifier le module Telegram.
* Ne pas ajouter de système de rôle.
* Ne pas ajouter de base de données.
* Ne pas ajouter de multi-user.
* Ne pas complexifier l’architecture.
* Ne pas dupliquer inutilement la sécurité si le module Telegram couvre déjà le besoin.
* Rester sur une sécurité minimale.
