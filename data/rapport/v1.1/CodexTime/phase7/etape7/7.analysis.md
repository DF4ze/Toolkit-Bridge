# PROMPT — Analyse Phase 7 Étape 7 — Gestion des erreurs Telegram workflow

## Contexte

Tu interviens sur le projet `Toolkit-Bridge`.

La Phase 7 vise l’intégration Telegram du workflow Codex.

Les étapes précédentes permettent maintenant :

* `/workflow` : tableau de bord workflow
* `/workflow_run` : lancer un workflow
* `/workflow_status` : consulter l’état
* `/workflow_summary` : consulter le summary ou recevoir le fichier
* `/workflow_resume` : reprendre après `WAITING_HUMAN`
* `/workflow_roadmap_load` : charger une roadmap
* sécurité minimale : bot `Cortex`, whitelist, warning si whitelist vide

L’orchestration est asynchrone, protégée par `runId`, et l’état est stocké en mémoire par `chatId`.

## Objectif

Analyser la gestion des erreurs côté Telegram workflow afin de rendre les échecs :

* clairs pour l’utilisateur ;
* sûrs, sans fuite technique ;
* exploitables pour debug ;
* cohérents entre les commandes.

L’objectif n’est pas de créer un système complexe, mais de stabiliser les erreurs courantes.

## Travail demandé

### 1. Inventaire des erreurs actuelles

Analyser les erreurs possibles pour :

* `/workflow_run`
* `/workflow_resume`
* `/workflow_status`
* `/workflow_summary`
* `/workflow_roadmap_load`
* `/workflow`

Identifier pour chaque cas :

* erreur possible ;
* message actuel ;
* message attendu ;
* données utiles à conserver en session.

### 2. Erreurs d’exécution workflow

Analyser les cas :

* exception Java pendant le run ;
* timeout ;
* `STOP_FAILURE`;
* `WAIT_HUMAN`;
* résultat inattendu ;
* completion tardive ignorée par `runId`.

Préciser ce qui doit être visible par l’utilisateur et ce qui doit seulement être loggé.

### 3. Erreurs de configuration

Analyser :

* `reportRootDirectory` absent ou invalide ;
* `reportVersion` absent ;
* bot `Cortex` mal configuré ;
* whitelist vide ;
* roadmap absente ;
* phase/étape manquantes.

### 4. Erreurs de fichiers

Analyser :

* roadmap introuvable ;
* summary absent ;
* summary trop long ;
* document non envoyé ;
* lecture workspace impossible ;
* accès path refusé.

### 5. Erreurs de concurrence

Analyser :

* double `/workflow_run`;
* double `/workflow_resume`;
* run en cours puis `/workflow_summary`;
* timeout puis completion tardive.

### 6. Standardisation des messages

Proposer un format d’erreur standard, par exemple :

```text
❌ Action impossible
Reason: ...
Try: ...
```

ou une version ASCII si besoin.

Définir :

* message utilisateur court ;
* message technique loggé ;
* commande utile suggérée.

### 7. Niveau de détail autorisé

Définir ce qui ne doit pas apparaître dans Telegram :

* stack trace ;
* tokens ;
* chemins absolus ;
* secrets ;
* sorties brutes trop longues ;
* erreurs système complètes.

Définir ce qui peut apparaître :

* statut ;
* raison courte ;
* action recommandée ;
* summary disponible ou non ;
* runId court.

### 8. Logs

Analyser les logs nécessaires :

* niveau `WARN` / `ERROR`;
* inclure `chatId`, `runId`, `project`, `phase`, `etape`;
* ne pas logguer secrets ;
* logguer les exceptions complètes côté serveur, pas côté Telegram.

### 9. Tests à prévoir

Proposer des tests pour :

* timeout ;
* exception runner ;
* double run ;
* missing roadmap ;
* missing summary ;
* path refusé ;
* message sans stacktrace ;
* message sans path absolu ;
* completion tardive ignorée.

### 10. Recommandations

Classer en :

#### À faire maintenant

Corrections simples et utiles.

#### À reporter

Gestion avancée, audit trail, persistance, retries, alerting.

### 11. Plan d’implémentation

Proposer un plan en 5 à 10 étapes maximum si des corrections sont nécessaires.

## Contraintes strictes

* Ne rien implémenter.
* Ne pas modifier le runner.
* Ne pas modifier la CLI.
* Ne pas modifier le module Telegram.
* Ne pas ajouter de base de données.
* Ne pas ajouter de système d’audit complet.
* Ne pas ajouter de retry automatique complexe.
* Ne pas exposer de détails techniques sensibles dans Telegram.
* Rester sur une gestion d’erreurs simple et cohérente.
