# PROMPT — Correction Phase 7 Étape 7 — UX summary trop long

À enregistrer :

`data/rapport/v1.1/CodexTime/Phase7/etape7/7.correction.md`

## Contexte

L’étape 7 est globalement validée.

La relecture a identifié une correction UX utile dans `WorkflowTelegramSummaryService`.

Quand un summary est trop long et que le fichier est réellement envoyé en document, le message utilisateur utilise actuellement un format d’erreur :

```text
Action impossible
Reason: Summary too long. Complete file sent.
```

C’est trompeur, car l’action a réussi.

## Objectif

Corriger uniquement le message utilisateur dans le cas :

```text
summary trop long + document envoyé avec succès
```

## Corrections à appliquer

### 1. Cas document envoyé

Dans `WorkflowTelegramSummaryService`, si `sendDocument(...)` réussit, retourner un message de succès via le renderer.

Exemple attendu :

```text
Action effectuée
Detail: Summary too long. Complete file sent.
Next: Open the attached document.
```

ou formulation équivalente déjà cohérente avec le renderer existant.

### 2. Cas document non envoyé

Si aucun `TelegramSender` n’est disponible ou si `sendDocument(...)` échoue, conserver un message d’erreur :

```text
Action impossible
Reason: Summary too long. Complete file could not be sent.
Try: Check the summary file directly.
```

### 3. Tests

Adapter les tests pour vérifier :

* summary trop long + sender disponible + `sendDocument` OK → message de succès ;
* summary trop long + sender indisponible → message d’erreur ;
* summary trop long + `sendDocument` exception → message d’erreur.

## Contraintes strictes

* ne pas modifier runner ;
* ne pas modifier CLI ;
* ne pas modifier module Telegram ;
* ne pas modifier la sanitization globale ;
* ne pas ajouter de nouvelle fonctionnalité ;
* ne pas changer la stratégie `2 chunks max puis document`.
