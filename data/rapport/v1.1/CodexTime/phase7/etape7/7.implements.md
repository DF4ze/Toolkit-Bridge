# PROMPT — Implémentation Phase 7 Étape 7 — Gestion des erreurs Telegram workflow

À enregistrer :

`data/rapport/v1.1/CodexTime/Phase7/etape7/7.implements.md`

## Contexte

Le système Telegram workflow gère déjà :

* `/workflow_run`
* `/workflow_resume`
* `/workflow_status`
* `/workflow_summary`
* `/workflow_roadmap_load`
* `/workflow`

Les erreurs sont globalement visibles, mais pas encore assez standardisées ni sécurisées.

Le rapport d’analyse a identifié trois besoins :

1. logger correctement les exceptions côté serveur ;
2. sanitiser les messages visibles dans Telegram ;
3. homogénéiser les messages d’erreur.

Un point additionnel doit être pris en compte : les erreurs de quota / rate-limit des providers IA ou de Codex.

## Objectif

Stabiliser la gestion des erreurs Telegram sans changer le moteur workflow.

## Travail demandé

### 1. Ajouter une sanitization des erreurs

Créer une logique simple, par exemple :

`WorkflowTelegramErrorSanitizer`

Responsabilités :

* supprimer ou masquer les stack traces ;
* supprimer les chemins absolus évidents ;
* supprimer les traces de tokens / secrets si détectables ;
* borner la longueur des messages visibles ;
* produire une raison courte utilisable dans Telegram.

Exemples à filtrer :

* `Exception`
* `\tat`
* chemins Windows type `C:\...`
* chemins Unix type `/home/...`
* chaînes très longues

Longueur cible recommandée :

```text
300 à 400 caractères max
```

### 2. Détecter quota / rate-limit

Ajouter une détection simple par patterns, sans créer de moteur complexe.

Patterns à reconnaître dans le message brut :

* `quota`
* `rate limit`
* `rate-limit`
* `too many requests`
* `usage limit`
* `limit reached`
* `429`
* `weekly limit`
* `5h limit`

Message utilisateur recommandé :

```text
Action impossible
Reason: Provider quota or rate limit reached.
Try: Wait and retry later, or switch provider/model.
```

Important :

* afficher ce message côté Telegram ;
* logger le message complet côté serveur.

### 3. Appliquer la sanitization avant stockage session

Dans les appels à :

* `sessionStore.failRun(...)`
* `sessionStore.completeRun(... lastMessage ...)`

Ne jamais stocker directement :

* `exception.getMessage()`
* `WorkflowStepResult.message()`

sans sanitization.

### 4. Logger les exceptions côté serveur

Dans `WorkflowTelegramOrchestrationService` :

* logger les exceptions runner ;
* logger les timeouts ;
* inclure les champs utiles :

  * `chatId`
  * `userId`
  * `runId`
  * `project`
  * `phase`
  * `etape`

Ne pas logger de secrets.

Les stack traces doivent rester côté serveur, jamais dans Telegram.

### 5. Homogénéiser les erreurs utilisateur

Utiliser autant que possible le format :

```text
Action impossible
Reason: ...
Try: ...
```

À appliquer notamment aux erreurs de :

* `/workflow_summary`
* `/workflow_run`
* `/workflow_resume`
* `/workflow_roadmap_load`

Ne pas réécrire toute l’UX, seulement harmoniser les erreurs.

### 6. Tests attendus

Ajouter des tests pour vérifier :

* une exception runner avec stack trace donne un message Telegram sans stack trace ;
* un message avec path Windows ne ressort pas tel quel ;
* un message avec path Unix ne ressort pas tel quel ;
* un message trop long est tronqué ;
* une erreur `rate limit` est reconnue ;
* une erreur `quota exceeded` est reconnue ;
* `STOP_FAILURE` stocke un message sanitisé ;
* timeout loggué et message utilisateur safe ;
* `/workflow_status` ne renvoie pas de stacktrace ni path absolu.

### 7. Contraintes strictes

* ne pas modifier le runner ;
* ne pas modifier la CLI ;
* ne pas modifier le module Telegram ;
* ne pas ajouter de DB ;
* ne pas ajouter d’audit trail complet ;
* ne pas ajouter de retry automatique ;
* ne pas créer de moteur complexe de classification ;
* ne pas exposer de détails techniques sensibles dans Telegram.
