# PROMPT — Analyse Phase 7 Étape 8 — Stabilisation Telegram workflow

## Contexte

Tu interviens sur le projet `Toolkit-Bridge`.

La Phase 7 vise l’intégration Telegram du workflow Codex.

Les étapes précédentes ont permis d’ajouter :

* `/workflow` : tableau de bord workflow
* `/workflow_run` : lancement async du workflow
* `/workflow_status` : vue synthétique de l’état
* `/workflow_summary` : affichage du summary, avec chunk/document fallback
* `/workflow_resume` : reprise après `WAITING_HUMAN`
* `/workflow_roadmap_load` : chargement sécurisé d’une roadmap
* sécurité minimale : whitelist Telegram + warning si whitelist vide
* gestion d’erreurs : sanitization, logs serveur, détection quota/rate-limit

L’objectif de cette étape est de stabiliser l’ensemble avant clôture de la Phase 7.

## Objectif

Analyser ce qu’il reste à faire pour rendre l’intégration Telegram fiable, cohérente et clôturable.

L’objectif n’est pas d’ajouter de grosses fonctionnalités, mais de vérifier :

* cohérence globale des commandes ;
* robustesse des états ;
* non-régression ;
* logs utiles ;
* tests de bout en bout ;
* documentation minimale ;
* dette restante à reporter clairement.

## Travail demandé

### 1. Inventaire final des commandes

Lister les commandes workflow actuelles :

* `/workflow`
* `/workflow_run`
* `/workflow_status`
* `/workflow_summary`
* `/workflow_resume`
* `/workflow_roadmap_load`

Pour chacune, vérifier :

* rôle ;
* préconditions ;
* sortie utilisateur ;
* erreurs gérées ;
* tests existants.

### 2. Cycle complet à valider

Analyser le cycle :

```text
roadmap load
→ workflow run
→ status
→ summary
→ WAITING_HUMAN éventuel
→ resume
→ status final
```

Identifier ce qui est déjà couvert par tests et ce qui manque.

### 3. Robustesse session

Vérifier :

* session par `chatId` ;
* `running`;
* `runId`;
* completion tardive ignorée ;
* timeout ;
* double run ;
* double resume ;
* redémarrage application = perte d’état acceptée ou à documenter.

### 4. Robustesse fichiers

Vérifier :

* roadmap load sécurisé ;
* summary sécurisé ;
* fallback document ;
* absence de chemins absolus dans UX ;
* comportement si fichier supprimé après run.

### 5. Robustesse erreurs

Vérifier :

* messages standardisés ;
* sanitization ;
* logs serveur ;
* quota/rate-limit ;
* absence stacktrace/token/path absolu dans Telegram.

### 6. Cohérence configuration

Vérifier :

* `WorkflowTelegramProperties`;
* `reportRootDirectory`;
* `reportVersion`;
* `timeoutMinutes`;
* bot `Cortex`;
* whitelist ;
* executor lifecycle.

Identifier ce qui doit être documenté.

### 7. Tests de stabilisation à prévoir

Proposer les tests utiles :

* test de cycle simulé `RUN → WAITING_HUMAN → RESUME → COMPLETED`;
* test de cycle `RUN → COMPLETED`;
* test `RUN → FAILED`;
* test summary long ;
* test double run ;
* test timeout ;
* test non-fuite UX ;
* test whitelist/documentation si applicable.

### 8. Documentation minimale

Identifier la doc à produire ou mettre à jour :

* commandes Telegram workflow ;
* configuration minimale ;
* sécurité ;
* limites connues ;
* comportement après redémarrage ;
* usage recommandé en chat privé.

### 9. Dette à reporter

Lister clairement ce qui ne doit pas être traité maintenant :

* persistance session ;
* multi-user avancé ;
* rôles ;
* boutons inline ;
* alias courts ;
* passage automatique d’étape ;
* parsing roadmap complet ;
* audit trail ;
* retry automatique complexe.

### 10. Plan d’implémentation

Proposer un plan court en 5 à 10 étapes maximum pour clôturer proprement la Phase 7.
