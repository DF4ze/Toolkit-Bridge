# PROMPT — Implémentation Phase 7 Étape 8 — Stabilisation finale

À enregistrer :

`data/rapport/v1.1/CodexTime/Phase7/etape8/8.implements.md`

## Contexte

Tu interviens sur `Toolkit-Bridge`.

La Phase 7 a ajouté l’intégration Telegram du workflow Codex.

Les commandes principales existent déjà :

* `/workflow`
* `/workflow_run`
* `/workflow_status`
* `/workflow_summary`
* `/workflow_resume`
* `/workflow_roadmap_load`

L’objectif de cette étape est de stabiliser et clôturer la Phase 7, sans ajouter de nouvelle fonctionnalité.

## Objectif

Renforcer la fiabilité de l’intégration Telegram avec :

* tests de cycle complet ;
* documentation minimale ;
* validation non-fuite ;
* vérification encodage ;
* clarification des limites connues.

## Travail demandé

### 1. Ajouter un test de cycle complet WAIT_HUMAN → RESUME

Créer ou compléter les tests pour simuler :

```text
roadmap load
→ workflow run
→ résultat WAIT_HUMAN
→ workflow resume
→ résultat CONTINUE / COMPLETED
```

Le test doit vérifier :

* session passe en `WAITING_HUMAN` après le run ;
* `lastSummaryPath` est mémorisé ;
* `/workflow_resume` est autorisé ;
* session passe en `COMPLETED` après resume ;
* `runId` reste cohérent ;
* aucune completion tardive ne casse l’état.

Utiliser un runner mocké/fake, sans lancer réellement Codex.

### 2. Ajouter un test RUN → COMPLETED

Tester un cycle simple :

```text
workflow run → CONTINUE → COMPLETED
```

Vérifier :

* session `COMPLETED`
* `running=false`
* message utilisateur cohérent
* summary path mémorisé si présent

### 3. Ajouter un test RUN → FAILED

Tester :

```text
workflow run → STOP_FAILURE → FAILED
```

Vérifier :

* session `FAILED`
* erreur sanitisée
* pas de stacktrace exposée
* pas de chemin absolu exposé

### 4. Ajouter test non-fuite cross-OS

Les tests actuels couvrent surtout les chemins Windows.

Ajouter un cas de type chemin Unix :

```text
/home/user/project/secret/file.md
```

Vérifier que `/workflow` et `/workflow_status` n’exposent pas de chemin absolu Unix.

### 5. Documenter la configuration Telegram workflow

Créer ou compléter une documentation Phase 7 indiquant clairement :

#### Config Telegram module

```text
telegram.enabled
telegram.bots[].id
telegram.bots[].token
telegram.bots[].polling-enabled
telegram.bots[].security.allowed-user-ids
```

#### Config workflow Telegram

```text
toolkit.telegram.workflow.reportRootDirectory
toolkit.telegram.workflow.reportVersion
toolkit.telegram.workflow.timeoutMinutes
```

Expliquer que ces propriétés sont distinctes.

### 6. Documenter les limites connues

Ajouter une section :

* session en mémoire : perdue au redémarrage ;
* usage en groupe : les messages/summaries peuvent être visibles par tous ;
* summary peut contenir des informations sensibles ;
* whitelist non vide recommandée ;
* pas de persistance ;
* pas de passage automatique de phase ;
* pas de parsing complet roadmap.

### 7. Vérifier encodage

Faire une passe sur les fichiers Telegram workflow :

* pas de mojibake ;
* UTF-8 cohérent ;
* éviter les caractères problématiques si nécessaire ;
* tests ne doivent pas dépendre fortement d’emojis.

### 8. Contraintes strictes

* ne pas ajouter de nouvelle commande ;
* ne pas modifier le runner ;
* ne pas modifier la CLI ;
* ne pas modifier le module Telegram ;
* ne pas ajouter de DB ;
* ne pas ajouter de persistance ;
* ne pas ajouter de boutons inline ;
* ne pas ajouter d’alias courts ;
* ne pas ajouter d’automatisation d’étape ;
* ne pas parser la roadmap ;
* rester sur tests + doc + cohérence.
