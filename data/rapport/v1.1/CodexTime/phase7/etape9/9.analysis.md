# PROMPT — Analyse Phase 7 Étape 9 — Point WebUI workflow

À enregistrer :

`data/rapport/v1.1/CodexTime/Phase7/etape9/9.analysis.md`

## Contexte

Tu interviens sur `Toolkit-Bridge`.

La Phase 7 a ajouté une interface Telegram permettant de piloter le workflow Codex :

* `/workflow`
* `/workflow_run`
* `/workflow_status`
* `/workflow_summary`
* `/workflow_resume`
* `/workflow_roadmap_load`

Avant de clôturer la Phase 7, il faut faire un point sur la partie WebUI existante.

## Objectif

Analyser si l’interface web actuelle expose ou permet de piloter le workflow Codex.

Le but est de comparer :

```text
UX Telegram actuelle
vs
UX Web actuelle
```

Et d’identifier ce qui manque côté WebUI.

## Travail demandé

### 1. Inventaire WebUI existant

Analyser le projet et identifier :

* pages web existantes ;
* controllers web ;
* templates Thymeleaf ;
* endpoints REST utilisés par la WebUI ;
* pages d’administration liées aux agents, tâches, traces, workflows, artefacts.

### 2. État workflow visible côté WebUI

Vérifier si la WebUI affiche :

* run en cours ;
* statut du workflow ;
* project ;
* phase ;
* étape ;
* lastRunId ;
* lastMessage ;
* lastError ;
* lastSummaryPath ;
* roadmap active ;
* état `WAITING_HUMAN`.

### 3. Interaction workflow côté WebUI

Vérifier si la WebUI permet déjà :

* lancer un workflow ;
* consulter le status ;
* lire un summary ;
* reprendre après `WAITING_HUMAN` ;
* charger une roadmap ;
* voir les erreurs sanitisées.

### 4. Comparaison Telegram / WebUI

Comparer les capacités :

| Capacité     | Telegram | WebUI   |
| ------------ | -------- | ------- |
| dashboard    | oui/non  | oui/non |
| run          | oui/non  | oui/non |
| status       | oui/non  | oui/non |
| summary      | oui/non  | oui/non |
| resume       | oui/non  | oui/non |
| roadmap load | oui/non  | oui/non |

### 5. Architecture recommandée

Analyser si la WebUI doit :

* réutiliser les services Telegram workflow existants ;
* utiliser une couche workflow plus générique ;
* rester séparée ;
* exposer uniquement de la lecture dans un premier temps.

Attention : ne pas coupler WebUI à Telegram.

### 6. Risques

Identifier les risques :

* duplication Telegram/WebUI ;
* logique workflow dispersée ;
* exposition d’informations sensibles ;
* actions dangereuses accessibles depuis web ;
* confusion entre état Telegram par `chatId` et état global workflow.

### 7. Recommandations

Classer :

#### À faire maintenant

Petites corrections ou documentation.

#### À reporter

Implémentation UI complète, boutons, pilotage avancé.

### 8. Plan possible

Proposer un plan en 5 à 10 étapes maximum pour une future phase WebUI, si nécessaire.

## Contraintes strictes

* Ne rien implémenter.
* Ne pas modifier Telegram.
* Ne pas modifier runner.
* Ne pas modifier CLI.
* Ne pas ajouter de nouvelle UI maintenant.
* Ne pas ajouter de DB.
* Rester sur analyse / audit / recommandations.
