# PROMPT — Analyse Phase 8 CodexCall Étape 1 — Registre projet persistant

## Contexte

Tu interviens sur `Toolkit-Bridge`, sous-système `CodexTime`.

CodexTime permet déjà de lancer un workflow via Telegram, mais il manque une brique essentielle : relier un nom logique de projet à son chemin réel sur disque.

Analyse préalable disponible :

`data/rapport/v1.1/CodexTime/phase8_CodexCall/project_path_codex_cli_analysis.md`

Cette analyse indique que le pipeline supporte déjà la variable :

`codexWorkingDirectory`

mais que l’intégration Telegram ne sait pas encore résoudre :

`projectName → projectPath`

## Objectif de l’étape 1

Analyser comment créer un **registre projet persistant** minimal.

Ce registre doit permettre de stocker en DB :

`projectName → projectPath`

Il sera utilisé plus tard par :

* `/workflow_project_set`
* `/workflow_run`
* `/workflow_resume`
* l’injection de `codexWorkingDirectory`

## Travail demandé

### 1. Analyser les conventions DB existantes

Lire le projet et identifier les conventions utilisées pour :

* entités JPA ;
* repositories ;
* services ;
* noms de tables ;
* champs `createdAt` / `updatedAt` ;
* éventuel `@Version` ;
* validation métier ;
* tests repository/service.

Identifier où placer proprement le futur registre projet.

### 2. Proposer le modèle de données

Proposer une entité simple, par exemple :

`WorkflowProjectEntity`

ou :

`CodexProjectEntity`

Champs attendus :

* `id`
* `projectName`
* `projectPath`
* `createdAt`
* `updatedAt`

À analyser :

* contrainte unique sur `projectName` ;
* normalisation du nom ;
* casse sensible ou non ;
* stockage du path en string absolue normalisée ;
* utilité ou non de `@Version`.

### 3. Proposer le repository

Définir le repository nécessaire :

* `findByProjectName(...)`
* éventuellement `existsByProjectName(...)`

Analyser si le nom doit être stocké normalisé pour éviter les doublons du type :

* `ToolkitBridge`
* `toolkitbridge`
* `ToolkitBridge`

### 4. Proposer le service registry

Analyser la création d’un service, par exemple :

`WorkflowProjectRegistryService`

Responsabilités :

* créer ou mettre à jour un projet ;
* résoudre un projet par nom ;
* normaliser le nom ;
* valider le path ;
* retourner un résultat exploitable par Telegram plus tard.

Ne pas implémenter Telegram dans cette étape.

### 5. Définir les règles de validation du nom projet

Proposer une règle simple :

* non null ;
* non blank ;
* trim ;
* longueur max raisonnable ;
* caractères autorisés si nécessaire.

Recommander une forme stable utilisable dans les commandes Telegram.

### 6. Définir les règles de validation du path

Le path doit :

* être non vide ;
* être valide pour l’OS ;
* être converti en absolu normalisé ;
* exister ;
* être un dossier ;
* être lisible ;
* être writable si Codex doit modifier le projet.

### 7. Définir les chemins dangereux à refuser

Analyser comment refuser les chemins dangereux sans sur-complexifier.

Règles attendues :

#### Windows

Refuser :

* racines disque : `C:\`, `D:\`, etc. ;
* dossiers système :
  * `C:\Windows`
  * `C:\Program Files`
  * `C:\Program Files (x86)`
  * `C:\Users`

#### Linux

Refuser :

* `/`
* `/bin`
* `/boot`
* `/dev`
* `/etc`
* `/lib`
* `/lib64`
* `/proc`
* `/root`
* `/sbin`
* `/sys`
* `/usr`
* `/var`

#### Home utilisateur

Refuser le dossier home directement, par exemple :

`/home/clement`

mais autoriser :

`/home/clement/projects/Toolkit-Bridge`

Sur Windows, analyser si une règle équivalente doit refuser :

`C:\Users\<user>`

tout en autorisant :

`C:\Users\<user>\Documents\Spring\Toolkit-Bridge`

### 8. Définir le comportement upsert

Comportement attendu :

* si `projectName` n’existe pas : création ;
* si `projectName` existe : remplacement de `projectPath` ;
* `createdAt` conservé ;
* `updatedAt` mis à jour.

Identifier comment tester ce comportement.

### 9. Définir les résultats métier du service

Le service ne doit pas exposer d’exceptions brutes à Telegram plus tard.

Proposer un résultat métier simple, par exemple :

* `WorkflowProjectRegistrationResult`
* `WorkflowProjectLookupResult`

Ou, si le style projet préfère les exceptions métier, l’indiquer clairement.

Le résultat doit permettre de distinguer :

* création ;
* mise à jour ;
* projet introuvable ;
* nom invalide ;
* path invalide ;
* path dangereux ;
* path non répertoire.

### 10. Tests à prévoir

Proposer les tests unitaires/repository nécessaires :

* création nouveau projet ;
* update projet existant ;
* nom vide refusé ;
* nom trim/normalisé ;
* path inexistant refusé ;
* path fichier refusé ;
* path répertoire accepté ;
* racine Windows refusée ;
* dossier système Windows refusé ;
* racine Linux refusée ;
* dossier système Linux refusé ;
* home direct refusé ;
* sous-dossier home accepté.

Préciser ce qui peut être testé indépendamment de l’OS avec des méthodes pures, et ce qui nécessite des tests conditionnels.

### 11. Risques

Identifier les risques :

* stocker des paths invalides ;
* casse/doublons de projectName ;
* validation trop stricte qui bloque un vrai projet ;
* validation trop permissive qui permet un dossier dangereux ;
* dépendance OS fragile dans les tests ;
* fuite future de path absolu côté Telegram.

### 12. Plan d’implémentation

Proposer un plan clair en 5 à 8 étapes maximum pour l’étape 1.

## Contraintes strictes

* Ne pas implémenter encore `/workflow_project_set`.
* Ne pas modifier `/workflow_run`.
* Ne pas modifier `/workflow_resume`.
* Ne pas modifier `CodexWorkflowClient`.
* Ne pas ajouter de WebUI.
* Ne pas ajouter d’abstraction `AgentCoder`.
* Ne pas exposer de path absolu côté UX.
* Ne pas refondre la configuration globale.
* Rester minimal, testable et aligné avec les conventions existantes.
