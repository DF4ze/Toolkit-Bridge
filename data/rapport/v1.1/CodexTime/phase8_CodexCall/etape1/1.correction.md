## Corrections demandées

### 1. Injecter `WorkflowProjectPathPolicy` comme bean Spring

Actuellement, `WorkflowProjectRegistryService` instancie probablement :

```java
new WorkflowProjectPathPolicy()
```

Remplacer par une injection Spring.

À faire :

* déclarer `WorkflowProjectPathPolicy` comme bean Spring, par exemple avec `@Component` ;
* injecter `WorkflowProjectPathPolicy` dans `WorkflowProjectRegistryService` ;
* conserver les tests unitaires existants ;
* adapter les tests si nécessaire.

Ne pas changer le comportement fonctionnel.

### 2. Supprimer l’import inutile

Dans :

`WorkflowProjectRegistryService`

Supprimer l’import inutilisé :

```java
java.nio.file.InvalidPathException
```

ou tout autre import devenu inutile.

### 3. Renforcer la policy Windows

La policy Windows ne doit pas être centrée uniquement sur `C:\`.

Elle doit refuser les dossiers système sur n’importe quel drive.

Refuser notamment :

```text
C:\Windows
D:\Windows
C:\Program Files
D:\Program Files
C:\Program Files (x86)
D:\Program Files (x86)
C:\Users
D:\Users
```

Règle recommandée :

* après le drive root, analyser le premier segment ;
* refuser si le premier segment est :

  * `Windows`
  * `Program Files`
  * `Program Files (x86)`
  * `Users`

La comparaison doit être case-insensitive.

Continuer à refuser :

* les racines disque `C:\`, `D:\`, etc. ;
* le home direct utilisateur ;
* mais autoriser les sous-dossiers home utilisateur comme :

  * `C:\Users\clement\Documents\Spring\Toolkit-Bridge`

Attention : si la règle “premier segment Users” refuse tout `C:\Users\...`, elle entrerait en conflit avec l’autorisation des sous-dossiers home. Il faut donc conserver l’exception : le home direct est refusé, mais ses sous-dossiers sont autorisés.

### 4. Tests complémentaires

Ajouter ou adapter des tests de policy pure :

* `D:\Windows` refusé ;
* `D:\Program Files` refusé ;
* `D:\Program Files (x86)` refusé ;
* `D:\Users` refusé ;
* `C:\Users\clement` refusé ;
* `C:\Users\clement\Documents\Spring\Toolkit-Bridge` accepté.
