# PROMPT — Implémentation Phase 8 CodexCall Étape 1 — Registre projet persistant

## Contexte

Tu interviens sur `Toolkit-Bridge`, sous-système `CodexTime`.

Une analyse préalable existe :

`data/rapport/v1.1/CodexTime/phase8_CodexCall/etape1/result_1_analysis.md`

Elle recommande de créer un registre projet persistant permettant de stocker :

```text
projectName → projectPath
```

Cette étape ne doit pas encore intégrer Telegram ni modifier `/workflow_run`.

## Objectif

Créer la base persistante et applicative du registre projet.

Ce registre devra permettre plus tard :

* `/workflow_project_set`
* résolution `projectName → projectPath`
* injection `codexWorkingDirectory`
* exécution Codex dans le bon dossier projet

## Décisions retenues

### Nom du modèle

Utiliser un nom générique orienté workflow :

```text
WorkflowProjectEntity
```

et non `CodexProjectEntity`, pour ne pas enfermer le modèle dans Codex uniquement.

### Champs

L’entité doit contenir :

* `id`
* `projectKey`
* `projectName`
* `projectPath`
* `createdAt`
* `updatedAt`

### Normalisation

* `projectName` conserve le nom affichable après trim.
* `projectKey` est la version normalisée :
  * trim ;
  * lowercase `Locale.ROOT`.

Exemple :

```text
ToolkitBridge → toolkitbridge
```

### Unicité

`projectKey` doit être unique.

### Pas de `@Version`

Ne pas ajouter `@Version` pour cette première version.

## Travail demandé

### 1. Créer l’entité JPA

Créer :

```text
WorkflowProjectEntity
```

Package recommandé :

```text
fr.ses10doigts.toolkitbridge.service.agent.workflow.runtime.project
```

Table recommandée :

```text
workflow_project
```

Champs :

* `id`
* `project_key`
* `project_name`
* `project_path`
* `created_at`
* `updated_at`

Contraintes :

* `project_key` unique ;
* `project_key` non null ;
* `project_name` non null ;
* `project_path` non null.

Ajouter `@PrePersist` / `@PreUpdate` pour timestamps, selon les conventions existantes.

### 2. Créer le repository

Créer :

```text
WorkflowProjectRepository
```

Méthodes :

```java
Optional<WorkflowProjectEntity> findByProjectKey(String projectKey);
```

Optionnel :

```java
boolean existsByProjectKey(String projectKey);
```

### 3. Créer les résultats métier

Créer des records ou classes simples :

```text
WorkflowProjectRegistrationResult
WorkflowProjectLookupResult
```

Ils doivent permettre de distinguer :

* succès / échec ;
* création / update ;
* projet trouvé / non trouvé ;
* projectKey ;
* projectName ;
* normalizedProjectPath ;
* reason en cas d’échec.

Ne pas exposer d’exception brute dans ces résultats.

### 4. Créer la policy de path dangereux

Créer une classe dédiée, par exemple :

```text
WorkflowProjectPathPolicy
```

Elle doit contenir une logique testable séparée du filesystem.

Objectif : refuser les chemins trop dangereux.

#### Windows

Refuser :

* racines disque : `C:\`, `D:\`, etc. ;
* `C:\Windows`
* `C:\Program Files`
* `C:\Program Files (x86)`
* `C:\Users`
* home direct de l’utilisateur, par exemple `C:\Users\clement`

Autoriser :

```text
C:\Users\clement\Documents\Spring\Toolkit-Bridge
```

#### Linux / Unix

Refuser :

* `/`
* `/bin`
* `/boot`
* `/dev`
* `/etc`
* `/lib`
* `/lib64`
* `/proc`
* `/root`
* `/sbin`
* `/sys`
* `/usr`
* `/var`
* home direct de l’utilisateur, par exemple `/home/clement`

Autoriser :

```text
/home/clement/projects/Toolkit-Bridge
```

La policy doit être testable sans dépendre de l’OS courant.

### 5. Créer le service registry

Créer :

```text
WorkflowProjectRegistryService
```

Responsabilités :

```java
registerOrUpdate(String projectName, String projectPath)
lookup(String projectName)
```

Le service doit :

* valider le nom ;
* normaliser le nom ;
* valider le path ;
* appliquer la policy chemins dangereux ;
* vérifier :
  * path existe ;
  * path est un dossier ;
  * path est lisible ;
  * path est writable ;
* convertir le path en absolu normalisé ;
* faire l’upsert DB ;
* conserver `createdAt` lors d’un update ;
* mettre à jour `updatedAt`.

### 6. Validation `projectName`

Règles :

* non null ;
* non blank ;
* trim ;
* max 120 caractères ;
* espaces interdits ;
* caractères autorisés :
  * lettres ;
  * chiffres ;
  * `.`
  * `_`
  * `-`

Regex possible :

```text
[A-Za-z0-9._-]+
```

### 7. Validation `projectPath`

Règles :

* non null ;
* non blank ;
* `Path.of(...)` doit réussir ;
* `toAbsolutePath().normalize()`;
* path dangereux refusé ;
* path inexistant refusé ;
* fichier refusé ;
* dossier non lisible refusé ;
* dossier non writable refusé.

### 8. Tests attendus

Ajouter tests unitaires pour :

#### Nom projet

* null refusé ;
* blank refusé ;
* trim appliqué ;
* lowercase projectKey ;
* espaces refusés ;
* caractères invalides refusés ;
* nom valide accepté.

#### Path policy pure

* root Windows refusé ;
* dossier système Windows refusé ;
* home Windows direct refusé ;
* sous-dossier home Windows accepté ;
* root Unix refusé ;
* dossier système Unix refusé ;
* home Unix direct refusé ;
* sous-dossier home Unix accepté.

#### Service registry avec `@TempDir`

* path inexistant refusé ;
* path fichier refusé ;
* path répertoire accepté ;
* création projet ;
* update projet existant ;
* lookup projet existant ;
* lookup projet inconnu.

#### Repository / DB

Ajouter un test d’intégration SQLite si cohérent avec les patterns existants :

* contrainte unique sur `projectKey` ;
* upsert réel create puis update.

### 9. Contraintes strictes

* Ne pas modifier `/workflow_resume`.
* Ne pas modifier `CodexWorkflowClient`.
* Ne pas ajouter de WebUI.
* Ne pas ajouter d’abstraction `AgentCoder`.
* Ne pas exposer de path absolu dans une UX.
* Ne pas refondre la configuration globale.

* Rester minimal et testable.
