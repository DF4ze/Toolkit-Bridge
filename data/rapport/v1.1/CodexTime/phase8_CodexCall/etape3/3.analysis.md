# PROMPT — Analyse Phase 8 CodexCall Étape 3 — Résolution projet dans `/workflow_run` et `/workflow_resume`

## Contexte

Tu interviens sur `Toolkit-Bridge`, sous-système `CodexTime`.

Les étapes précédentes de la Phase 8 ont ajouté :

* un registre projet persistant `projectName → projectPath` ;
* un service `WorkflowProjectRegistryService` ;
* une commande Telegram `/workflow_project_set` permettant de créer ou mettre à jour un projet.

La commande `/workflow_project_set` est validée.

Il faut maintenant utiliser ce registre pendant l’exécution du workflow.

## Objectif de l’étape 3

Analyser comment résoudre correctement le projet pendant :

```text
/workflow_run
/workflow_resume
```

afin de récupérer le `projectPath` associé au `projectName`, le stocker en session si pertinent, puis préparer son injection future comme `codexWorkingDirectory`.

Attention : dans cette étape, on ne modifie pas encore `CodexWorkflowClient`.

## Règles fonctionnelles attendues

### `/workflow_run`

Si la commande contient :

```text
project=ToolkitBridge
```

alors :

1. chercher `ToolkitBridge` dans le registre projet ;
2. si trouvé :
   * récupérer `projectPath` ;
   * mettre à jour la session Telegram avec `projectName` + `projectPath` ;
   * continuer la résolution normale phase/etape ;
3. si non trouvé :
   * refuser le run avec un message clair.

Si la commande ne contient pas `project=...` :

1. vérifier si la session contient déjà un projet exploitable ;
2. si `projectName + projectPath` sont présents en session :
   * réutiliser ce projet ;
3. si la session contient `projectName` mais pas `projectPath` :
   * tenter un lookup DB ;
4. si aucun projet n’est exploitable :
   * refuser avec message clair.

### `/workflow_resume`

Le resume doit :

1. réutiliser le `projectPath` de session ;
2. si absent mais `projectName` présent :
   * tenter un lookup DB ;
3. si toujours absent :
   * refuser avec message clair ;
4. ne jamais changer de projet pendant un resume.
