# PROMPT — Correction Phase 8 CodexCall Étape 3 — Stabilisation résolution projet

## Contexte

Tu interviens sur `Toolkit-Bridge`, sous-système `CodexTime`.

L’étape 3 a ajouté :

* `projectPath` dans `WorkflowTelegramSession` ;
* résolution `projectName → projectPath` dans `/workflow_run` ;
* résolution projet dans `/workflow_resume` ;
* stockage en session ;
* aucune fuite du path dans Telegram.

La review valide fonctionnellement le lot, mais remonte deux corrections qualité.

## Objectif

Corriger uniquement les fragilités de qualité, sans modifier le comportement fonctionnel.

## Corrections demandées

### 1. Remplacer le string-matching sur les erreurs du resolver

Dans `WorkflowTelegramOrchestrationService`, supprimer toute logique du type :

```java
error.toLowerCase().contains(...)
```

utilisée pour détecter une erreur de projet manquant.

À la place, ajouter un signal structuré minimal dans le résultat de résolution.

Option recommandée :

Créer un enum :

```java
WorkflowTelegramRunTargetErrorCode
```

Valeurs minimales :

```text
MISSING_PROJECT
MISSING_PHASE_OR_ETAPE
INVALID_PHASE_OR_ETAPE
```

Puis enrichir :

```java
WorkflowTelegramRunTarget
```

avec un champ optionnel :

```java
WorkflowTelegramRunTargetErrorCode errorCode
```

Règles :

* les cas d’erreur existants doivent conserver leur message utilisateur ;
* l’orchestration doit utiliser `errorCode`, pas le texte libre, pour savoir si elle doit transformer l’erreur en :

```text
No project configured for this workflow session
```

* ne pas ajouter de dépendance DB au resolver.

### 2. Ajouter un overload `updateContext(...)`

Dans `WorkflowTelegramSessionStore`, ajouter ou restaurer une surcharge :

```java
updateContext(chatId, userId, projectName, phase, etape, roadmapPath)
```

Cette surcharge doit déléguer à la version complète (celle qui permet `projectPath`) avec `projectPath=null`.

Objectif :

* réduire la verbosité ;
* éviter les erreurs d’ordre d’arguments ;
* préserver la compatibilité interne pour les appels qui n’ont pas besoin de `projectPath`.

### 3. Tests attendus

Adapter ou ajouter les tests pour vérifier :

* le resolver retourne un `errorCode` structuré pour projet manquant ;
* l’orchestration ne dépend plus du texte d’erreur pour détecter le projet manquant ;
* les messages utilisateur restent identiques ;
* l’overload `updateContext(...)` fonctionne comme avant ;
* les tests existants continuent de passer.
