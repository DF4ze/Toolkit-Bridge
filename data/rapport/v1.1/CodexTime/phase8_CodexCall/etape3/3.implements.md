# PROMPT — Implémentation Phase 8 CodexCall Étape 3 — Résolution projet dans `/workflow_run` et `/workflow_resume`

## Contexte

Tu interviens sur `Toolkit-Bridge`, sous-système `CodexTime`.

Les étapes précédentes de la Phase 8 ont ajouté :

* un registre projet persistant `projectName → projectPath` ;
* un service `WorkflowProjectRegistryService` ;
* une commande Telegram `/workflow_project_set`.

L’analyse de l’étape 3 est disponible ici :

`data/rapport/v1.1/CodexTime/phase8_CodexCall/etape3/result_3_analysis.md`

Elle recommande de résoudre le `projectPath` dans `/workflow_run` et `/workflow_resume`, puis de le stocker en session.

## Objectif

Permettre à `/workflow_run` et `/workflow_resume` de disposer d’un `projectPath` fiable, résolu depuis le registre projet.

Cette étape prépare l’injection future de :

```text
codexWorkingDirectory
```

mais ne doit pas encore modifier `CodexWorkflowClient`.

## Décisions retenues

### Resolver logique

`WorkflowTelegramRunTargetResolver` doit rester pur :

* pas de DB ;
* pas de repository ;
* pas de registry service ;
* il continue seulement à résoudre `projectName`, `phase`, `etape`.

### Résolution projet

La résolution `projectName → projectPath` doit être faite dans :

```text
WorkflowTelegramOrchestrationService
```

ou dans un helper/service interne appelé par lui.

### Session

Ajouter un champ interne :

```java
Path projectPath
```

dans `WorkflowTelegramSession`.

Règles :

* optionnel ;
* utilisé uniquement côté runtime ;
* ne jamais afficher la valeur dans Telegram ;
* ne pas afficher non plus `Project path: configured/missing` pour l’instant ;
* si `projectName` change, remplacer aussi `projectPath`.

## Travail demandé

### 1. Étendre `WorkflowTelegramSession`

Ajouter :

```java
Path projectPath
```

Adapter :

* constructeur / record ;
* méthodes factory éventuelles ;
* tests existants.

### 2. Étendre `WorkflowTelegramSessionStore`

Modifier `updateContext(...)` pour permettre de mettre à jour :

* `projectName`
* `phase`
* `etape`
* `roadmapPath`
* `projectPath`

Règles :

* si un nouveau `projectName` est fourni avec un `projectPath`, stocker les deux ;
* si le projet change, ne pas conserver l’ancien `projectPath` ;
* éviter toute incohérence `projectName A` + `projectPath B`.

### 3. Ajouter une résolution projet dans `/workflow_run`

Dans `WorkflowTelegramOrchestrationService.startRun(...)`, appliquer les règles Cas A/B/C/D décrites.

### 4. Ajouter une résolution projet dans `/workflow_resume`

Dans `resume(...)` : conserver les préconditions existantes et appliquer la résolution depuis la session + lookup DB si nécessaire.

### 5. Ne pas afficher `projectPath`

Vérifier que `/workflow` et `/workflow_status` et messages run/resume n’exposent jamais de paths absolus.

### 6. Ne pas injecter encore `codexWorkingDirectory`

Ne pas modifier le contexte d’exécution pour l’instant.

### 7. Tests attendus

Ajouter/adapter les tests session/store, orchestration run/resume, et non-fuite.

## Contraintes strictes

* Ne pas modifier l’appel CLI Codex.
* Ne pas injecter encore `codexWorkingDirectory`.
* Ne pas exposer `projectPath` dans Telegram.
* Ne pas ajouter `Project path: configured/missing`.

* Ne pas ajouter d’abstraction `AgentCoder`.

* Ne pas refondre `WorkflowTelegramRunTargetResolver`.
