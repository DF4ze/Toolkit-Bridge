# PROMPT — Analyse Phase 9 Logging Étape 1 — Logs Telegram et orchestration

## Contexte

Tu interviens sur `Toolkit-Bridge`, sous-système `CodexTime`.

La Phase 9 vise à ajouter une journalisation intelligente dans CodexTime.

Le but n'est pas d'ajouter des logs partout, mais de rendre visible le chemin critique du workflow.

Cette étape 1 est limitée à la couche Telegram et orchestration.

## Objectif de l'étape 1

Analyser où ajouter des logs utiles dans :

* `WorkflowTelegramOrchestrationService`
* `WorkflowTelegramController`
* `WorkflowTelegramProjectService`
* `WorkflowTelegramRoadmapService`

Les logs doivent permettre de comprendre :

* quelles commandes Telegram importantes sont appelées ;
* quand un workflow est demandé ;
* quand un workflow est refusé ;
* quand un resume est demandé ;
* quand un workflow se termine ;
* quand une roadmap est chargée ;
* quand un projet est enregistré ou mis à jour ;
* quand une erreur technique est réellement levée.

## Exigence technique

Utiliser Lombok :

```java
@Slf4j
```

Si une classe utilise encore :

```java
LoggerFactory.getLogger(...)
```

analyser sa migration vers :

```java
@Slf4j
```

Ne pas ajouter de framework de logging.

## Travail demandé

### 1. Analyser `WorkflowTelegramOrchestrationService`

Identifier :

* logs existants ;
* éventuelle utilisation de `LoggerFactory` ;
* méthodes principales :
  * `startRun`
  * `resume`
  * `executeRun`
  * `executeResume`
  * `handleResult`
  * méthodes de refus / erreurs si présentes.

Proposer des logs :

#### INFO

Pour :

* workflow run demandé / accepté ;
* workflow resume demandé / accepté ;
* workflow terminé ;
* décision finale :
  * `CONTINUE`
  * `WAIT_HUMAN`
  * `STOP_FAILURE`
  * autre décision si présente.

#### WARN

Pour :

* run déjà en cours ;
* projet inconnu ;
* absence de projet configuré ;
* resume refusé ;
* session incohérente ;
* roadmap absente si cela concerne le run.

#### ERROR

Uniquement pour :

* exception réelle ;
* erreur async ;
* échec technique empêchant le workflow de continuer.

#### DEBUG

Pour :

* clés du contexte construit, sans valeurs sensibles ;
* résolution interne du projet, sans path absolu ;
* runId / status si utile.

### 2. Analyser `WorkflowTelegramController`

Identifier les commandes existantes :

* `/workflow`
* `/workflow_run`
* `/workflow_status`
* `/workflow_summary`
* `/workflow_resume`
* `/workflow_roadmap_load`
* `/workflow_project_set`

Proposer une stratégie :

#### INFO uniquement pour les commandes à effet

* `/workflow_run`
* `/workflow_resume`
* `/workflow_project_set`
* `/workflow_roadmap_load`

#### DEBUG ou aucun log pour les commandes de lecture

* `/workflow`
* `/workflow_status`
* `/workflow_summary`

Ne pas logger les arguments bruts si ceux-ci peuvent contenir un path absolu.

### 3. Analyser `WorkflowTelegramProjectService`

Identifier :

* méthode qui reçoit `/workflow_project_set` ;
* appel à `WorkflowProjectRegistryService` ;
* mapping succès / erreur.

Proposer :

#### INFO

* projet enregistré ;
* projet mis à jour.

#### WARN

* nom manquant ;
* path manquant ;
* path invalide ;
* path dangereux ;
* refus registry.

Ne pas logger `projectPath`.

### 4. Analyser `WorkflowTelegramRoadmapService`

Identifier :

* méthode de chargement roadmap ;
* validation du path ;
* erreurs possibles ;
* message utilisateur.

Proposer :

#### INFO

* roadmap chargée avec succès.

#### WARN

* roadmap absente ;
* path refusé ;
* extension invalide ;
* lecture impossible.

Ne pas logger le path absolu en INFO.

### 5. Définir les champs à logger

Proposer une liste courte de champs utiles :

* `chatId`
* `userId`
* `botId`
* `runId`
* `projectName`
* `phase`
* `etape`
* `decision`
* `status`
* `reason` courte et sanitisée

Ne pas logger :

* `projectPath`
* `roadmapPath`
* path absolu
* token Telegram
* prompt
* contenu de fichier
* summary
* stdout/stderr complets.

### 6. Définir les messages recommandés

Proposer des patterns concrets.

Exemples attendus :

```java
log.info("Workflow run requested: chatId={}, runId={}, project={}, phase={}, etape={}",
        chatId, runId, projectName, phase, etape);
```

```java
log.warn("Workflow run rejected: chatId={}, reason={}", chatId, reason);
```

```java
log.info("Workflow completed: chatId={}, runId={}, decision={}",
        chatId, runId, decision);
```

```java
log.error("Workflow execution failed: chatId={}, runId={}", chatId, runId, e);
```

Adapter ces messages au code réel.

### 7. Vérifier les risques de fuite

Analyser les risques :

* path absolu dans les args Telegram ;
* path absolu dans les erreurs registry ;
* roadmapPath exposé ;
* stacktrace trop verbeuse ;
* logs INFO trop nombreux ;
* messages utilisateur copiés tels quels.

Proposer des garde-fous simples.

### 8. Tests / vérifications à prévoir

Proposer ce qu'il faut vérifier :

* compilation avec `@Slf4j` ;
* pas de logs sur arguments bruts contenant path ;
* pas de changement comportemental ;
* tests existants toujours OK.

Ne pas demander de tests qui vérifient exactement les messages de logs.

### 9. Plan d'implémentation

Proposer un plan court en 4 à 6 étapes maximum.

## Contraintes strictes

* Ne rien implémenter dans cette analyse.
* Ne pas modifier le comportement métier.
* Ne pas ajouter de logs partout mécaniquement.
* Ne pas logger les paths absolus en INFO.
* Ne pas logger les prompts.
* Ne pas logger les tokens.
* Ne pas logger le contenu des fichiers.
* Ne pas logger stdout/stderr complets.
* Ne pas transformer les logs en UX utilisateur.
* Ne pas ajouter de framework de logging.
* Utiliser `@Slf4j`.
* Rester sobre.
