# PROMPT — Implémentation Phase 9 Logging Étape 1 — Logs Telegram et orchestration

## Contexte

Tu interviens sur `Toolkit-Bridge`, sous-système `CodexTime`.

La Phase 9 vise à ajouter une journalisation intelligente et sobre dans CodexTime.

Cette étape 1 concerne uniquement la couche Telegram et orchestration.

Analyse préalable :
`data/rapport/v1.1/CodexTime/phase9_Logging/etape1/result_1_analysis.md`

Classes concernées :

* `WorkflowTelegramOrchestrationService`
* `WorkflowTelegramController`
* `WorkflowTelegramProjectService`
* `WorkflowTelegramRoadmapService`

## Objectif

Ajouter des logs utiles pour rendre visibles :

* les commandes Telegram importantes ;
* les runs demandés / acceptés / refusés ;
* les resumes demandés / acceptés / refusés ;
* les décisions finales du workflow ;
* les projets enregistrés ou mis à jour ;
* les roadmaps chargées ou refusées.

Ne pas modifier le comportement métier.

## Exigence technique

Utiliser Lombok :

```java
@Slf4j
```

Si une classe utilise encore :

```java
LoggerFactory.getLogger(...)
```

la migrer vers `@Slf4j`.

Ne pas ajouter de framework de logging.

## 1. `WorkflowTelegramOrchestrationService`

### 1.1 Migration vers `@Slf4j`

Si la classe contient :

```java
private static final Logger log = LoggerFactory.getLogger(...)
```

alors :

* supprimer ce champ ;
* supprimer les imports `Logger` / `LoggerFactory` ;
* ajouter `@Slf4j` sur la classe ;
* conserver les appels `log.*` existants.

### 1.2 Logs sur `startRun`

Ajouter des logs `WARN` sur les refus :

* run déjà en cours ;
* projet inconnu ;
* projet non configuré ;
* target invalide ;
* session incohérente si applicable.

Exemples :

```java
log.warn("Workflow run rejected: chatId={}, reason={}", chatId, reason);
```

ou plus spécifique :

```java
log.warn("Workflow run rejected - unknown project: chatId={}, project={}", chatId, projectName);
```

Ajouter un log `INFO` quand le run est accepté et effectivement lancé :

```java
log.info("Workflow run started: chatId={}, runId={}, project={}, phase={}, etape={}",
        chatId, runId, target.projectName(), target.phase(), target.etape());
```

Ne pas logger :

* `projectPath` ;
* `roadmapPath` ;
* `reportRootDirectory` ;
* variables de contexte en valeurs.

### 1.3 Logs sur `resume`

Ajouter des logs `WARN` sur les refus :

* déjà en cours ;
* pas en `WAIT_HUMAN` ;
* contexte incomplet ;
* projet absent ;
* project path manquant.

Ajouter un log `INFO` quand le resume est accepté :

```java
log.info("Workflow resume started: chatId={}, runId={}, project={}, phase={}, etape={}",
        chatId, runId, session.projectName(), session.phase(), session.etape());
```

### 1.4 Logs sur résultat final

Dans `handleResult` ou méthode équivalente, ajouter un log `INFO` pour les décisions finales :

```java
log.info("Workflow completed: chatId={}, runId={}, decision={}",
        chatId, runId, decision);
```

Si le résultat est null ou inattendu :

```java
log.warn("Workflow returned null or unexpected result: chatId={}, runId={}", chatId, runId);
```

Conserver les `ERROR` existants pour les exceptions techniques.

## 2. `WorkflowTelegramController`

La classe possède déjà `@Slf4j`.

Ajouter des logs `INFO` uniquement pour les commandes à effet :

* `/workflow_run`
* `/workflow_resume`
* `/workflow_roadmap_load`
* `/workflow_project_set`

### `/workflow_run`

Logger uniquement les champs parsés :

```java
log.info("Command /workflow_run: chatId={}, userId={}, project={}, phase={}, etape={}",
        chatId, userId, projectName, phase, etape);
```

### `/workflow_resume`

```java
log.info("Command /workflow_resume: chatId={}, userId={}", chatId, userId);
```

### `/workflow_roadmap_load`

```java
log.info("Command /workflow_roadmap_load: chatId={}, userId={}, project={}",
        chatId, userId, projectName);
```

Ne pas logger `path`.

### `/workflow_project_set`

```java
log.info("Command /workflow_project_set: chatId={}, userId={}", chatId, userId);
```

Ne pas logger `ctx.getArgs()`.

Ne pas ajouter de log `INFO` pour :

* `/workflow`
* `/workflow_status`
* `/workflow_summary`

## 3. `WorkflowTelegramProjectService`

Ajouter `@Slf4j`.

Ajouter des logs :

### Succès

```java
log.info("Workflow project registered: name={}", result.projectName());
```

ou :

```java
log.info("Workflow project updated: name={}", result.projectName());
```

### Refus

```java
log.warn("Workflow project set rejected: name={}, reason={}", name, sanitizedReason);
```

Important :

* utiliser `sanitizeReason(...)` avant de logger une raison ;
* ne jamais logger le path brut ;
* ne jamais logger `normalizedProjectPath`.

## 4. `WorkflowTelegramRoadmapService`

La classe possède déjà `@Slf4j`.

### Succès

Si un log `DEBUG` existe sur le succès de chargement, le passer en `INFO` si le chemin est bien relatif/safe.

Exemple :

```java
log.info("Roadmap loaded: project={}, path={}", projectName, safeRelative);
```

`safeRelative` ou équivalent doit être un chemin relatif, jamais un path absolu.

### Refus / erreurs récupérables

Ajouter des logs `WARN` pour :

* roadmap absente ;
* extension invalide ;
* fichier vide ;
* path refusé ;
* fichier non lisible ;
* workspace root indisponible.

Exemples :

```java
log.warn("Roadmap rejected - invalid extension: chatId={}", chatId);
```

```java
log.warn("Roadmap rejected - forbidden path: chatId={}", chatId);
```

Ne jamais logger :

* path absolu résolu ;
* sharedRoot ;
* contenu du fichier ;
* message utilisateur complet.

## Règles de confidentialité obligatoires

Avant de valider, relire tous les `log.*` ajoutés.

Interdits :

* `projectPath` ;
* `roadmapPath` absolu ;
* `reportRootDirectory` ;
* `ctx.getArgs()` ;
* path brut utilisateur ;
* token Telegram ;
* prompt ;
* contenu de fichier ;
* contenu summary ;
* message utilisateur complet.

Autorisé :

* `chatId` ;
* `userId` ;
* `runId` ;
* `projectName` ;
* `phase` ;
* `etape` ;
* `decision` ;
* `status` ;
* raison courte sanitisée ;
* chemin relatif safe uniquement pour roadmap.

## Tests et validation

Ne pas ajouter de tests fragiles sur le texte exact des logs.

À faire :

* vérifier compilation ;
* lancer les tests existants ;
* vérifier manuellement les nouveaux logs.

Commande attendue :

```text
./mvnw test
```

ou Windows :

```text
.\mvnw.cmd test
```

## Contraintes strictes

* Ne pas modifier le comportement métier.
* Ne pas modifier les messages Telegram.
* Ne pas modifier la logique de session.
* Ne pas modifier la résolution projet.
* Ne pas modifier `CodexWorkflowClient`.
* Ne pas logger les arguments bruts Telegram.
* Ne pas logger de paths absolus en INFO.
* Ne pas ajouter de logs sur les commandes de lecture fréquentes.
* Ne pas ajouter de nouveau framework.
* Utiliser `@Slf4j`.
