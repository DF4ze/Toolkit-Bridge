# PROMPT — Implémentation Phase 9 Logging Étape 2 — Logs runner, orchestrator et steps métier

## Contexte

Tu interviens sur `Toolkit-Bridge`, sous-système `CodexTime`.

La Phase 9 vise à ajouter une journalisation intelligente, sobre et utile.

L'étape 1 a déjà ajouté les logs côté Telegram et orchestration.

Cette étape 2 concerne le cœur métier du workflow :

* runner ;
* orchestrator ;
* steps Codex ;
* validation Maven.

## Objectif

Ajouter des logs permettant de suivre le déroulé interne du workflow :

```text
run
→ analysis
→ review
→ correction éventuelle
→ validation Maven
→ retry éventuel
→ WAIT_HUMAN / STOP_FAILURE / succès
```

Les logs doivent aider à comprendre :

* quelle étape métier démarre ;
* quelle décision est retournée ;
* quand Codex est appelé ;
* quand Maven est lancé ;
* quand une correction est déclenchée ;
* quand un retry est utilisé ;
* quand un `WAIT_HUMAN` est produit ;
* quand un échec final arrive.

## Classes concernées

Analyser et instrumenter uniquement si présentes :

* `AnalysisReviewWorkflowRunner`
* `WorkflowOrchestrator`
* `GlobalAnalysisStep`
* `GlobalReviewStep`
* `CorrectionStep`
* `BuildErrorCorrectionStep`
* `MavenValidationStep`

## Exigence technique

Utiliser Lombok :

```java
@Slf4j
```

Ajouter l'annotation sur les classes qui n'ont pas encore de logger.

Ne pas ajouter de framework de logging.

## Règles de logs

### INFO

Utiliser `INFO` pour les transitions métier importantes :

* démarrage d'un run ;
* démarrage d'un resume ;
* appel Codex démarré ;
* appel Codex terminé ;
* validation Maven démarrée ;
* validation Maven terminée ;
* correction déclenchée ;
* limite de retry atteinte ;
* workflow terminé.

### DEBUG

Utiliser `DEBUG` pour les détails de diagnostic :

* step exécutée ;
* décision retournée ;
* retry count ;
* durée ;
* exit code ;
* taille stdout/stderr ;
* clés du contexte uniquement, jamais les valeurs sensibles.

### WARN

Utiliser `WARN` pour les situations récupérables ou nécessitant une action :

* `WAIT_HUMAN` ;
* validation Maven échouée mais correction possible ;
* retry déclenché ;
* timeout ;
* summary non généré mais non bloquant.

### ERROR

Utiliser `ERROR` uniquement pour :

* exception réelle ;
* échec technique final ;
* `STOP_FAILURE` technique.

## Confidentialité stricte

Ne jamais logger :

* prompt Codex ;
* contenu analysé ;
* contenu de fichier ;
* rapport complet ;
* summary complet ;
* stdout/stderr complets ;
* `buildErrorSummary` ;
* token ;
* clé API ;
* secret.

Autorisé :

* `runId` ;
* `phase` ;
* `etape` ;
* `decision` ;
* `status` ;
* `durationMs` ;
* `exitCode` ;
* `retryCount` ;
* `retryMax` ;
* `stdoutLen` ;
* `stderrLen` ;
* noms de classes / steps.

Les chemins absolus ne doivent pas être loggés en `INFO`.

## Travail demandé

### 1. `AnalysisReviewWorkflowRunner`

Ajouter `@Slf4j` si absent.

Ajouter des logs `INFO` pour :

* démarrage d'un run complet ;
* démarrage d'un resume / correction après review ;

Ajouter des logs `WARN` pour :

* contenu des artifacts ;

### 2. `WorkflowOrchestrator`

Ajouter `@Slf4j` si absent.

Ajouter uniquement des logs `DEBUG`.

Logger :

* step démarrée ;
* step terminée ;
* décision retournée ;
* correction optionnelle déclenchée.

Exemples :

```java
log.debug("Executing workflow step: runId={}, step={}", runId, step.getClass().getSimpleName());
```

```java
log.debug("Workflow step completed: runId={}, step={}, decision={}",
        runId, step.getClass().getSimpleName(), result.decision());
```

Ne pas logger :

* contenu de `WorkflowStepResult.data` ;
* message complet si celui-ci peut contenir du contenu métier ;
* artifacts complets.
