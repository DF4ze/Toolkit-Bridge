**v1.1 → Phase 1 → Étape 4 → Lot 1 — Suppression des fuites de secrets**

---

## 🎯 Objectif de ce prompt

Réaliser une **analyse précise et exhaustive** des fuites potentielles de secrets dans les logs.

⚠️ IMPORTANT :

* Tu dois **analyser uniquement**
* Tu ne dois **rien modifier**
* Tu ne dois **rien implémenter**

---

## 🔍 Contexte

L’analyse globale précédente a identifié plusieurs problèmes :

* master token loggé en clair (`AdminTokenService`)
* API keys agent loggées en clair (`AgentAccountInitializer`)
* risque global de logs contenant des données sensibles

Ce lot vise à :
👉 identifier **toutes les fuites réelles et potentielles**

---

## 🧠 Ce que tu dois faire

### 1. Analyse ciblée des zones critiques

Inspecte en priorité :

#### a) Sécurité admin

* `AdminTokenService`
* `AdminTokenInitializer`
* `AdminAuthenticationService`

#### b) Comptes / API keys

* `AgentAccountInitializer`
* toute classe manipulant des clés API

#### c) Logs techniques

* services contenant `log.info`, `log.debug`, `log.warn`, `log.error`
* notamment :

    * services security
    * services configuration
    * services runtime / bootstrap

---

### 2. Détection des fuites

Tu dois identifier tous les cas où :

* une valeur sensible est loggée en clair :

    * token
    * api key
    * secret
    * password
* une valeur sensible pourrait être loggée indirectement :

    * via toString()
    * via objets complets
    * via logs debug trop verbeux

---

### 3. Classification des problèmes

Pour chaque problème identifié, tu dois préciser :

* fichier + ligne
* type de donnée exposée
* niveau de gravité :

    * CRITIQUE (exposition directe)
    * ÉLEVÉ (exposition probable)
    * MOYEN (exposition indirecte possible)
* contexte du log (startup, erreur, debug…)

---

### 4. Analyse des patterns de logs

Identifier :

* s’il existe une convention de log
* s’il existe déjà une forme de masquage
* s’il y a des incohérences

---

### 5. Identification des risques indirects

Tu dois aussi analyser :

* objets contenant des secrets qui pourraient être loggés ailleurs
* DTO ou entités contenant :

    * apiKey
    * token
    * secret
* risques liés à `toString()`

---

### 6. Proposition d’approche de correction

⚠️ Sans implémenter

Tu dois proposer :

* une stratégie simple de masquage
* une règle claire :

    * ce qui doit être loggé
    * ce qui ne doit jamais l’être
* les zones à corriger en priorité

---

### 7. Découpage technique du lot

Même si le lot est petit, propose un sous-découpage :

* corrections critiques immédiates
* corrections secondaires
* améliorations optionnelles
