# Prompt Codex — Analyse Lot 2

## v1.1 / Phase 1 / Étape 4 / Lot 2 (Rate limiting login)

Tu travailles sur le repository **Toolkit-Bridge / Marcel**.

Nous sommes dans :
**v1.1 → Phase 1 → Étape 4 → Lot 2 — Rate limiting du login admin**

---

## 🎯 Objectif de ce prompt

Réaliser une **analyse précise de l’intégration d’un rate limiting sur le login admin**, sans implémenter.

⚠️ IMPORTANT :

* Tu dois **analyser uniquement**
* Tu ne dois **rien modifier**
* Tu ne dois **rien implémenter**

---

## 🔍 Contexte

Le système actuel possède :

* un endpoint `POST /login`
* une authentification basée sur token maître
* une session serveur après login
* aucun mécanisme de protection contre brute force

👉 Risque :

* tentative illimitée de login

---

## 🎯 Objectif du lot

Ajouter un **rate limiting simple, robuste et local** sur le login admin.

⚠️ Contraintes importantes :

* pas de dépendance externe (pas Redis, pas Bucket4j, etc.)
* solution en mémoire
* implémentation simple
* aucun impact sur le reste du système

---

## 🧠 Ce que tu dois analyser

### 1. Flux actuel du login

Identifier précisément :

* où arrive la requête (`LoginController`)
* comment est appelée l’authentification
* comment sont gérées les erreurs de login
* à quel moment on peut intercepter la tentative

---

### 2. Points d’insertion possibles

Tu dois proposer et comparer :

* insertion dans `LoginController`
* insertion dans `AdminAuthenticationService`
* ajout d’un filtre HTTP
* autre option pertinente

Pour chaque option :

* avantages
* inconvénients
* impact sur le code existant

---

### 3. Stratégie de rate limiting

Proposer une stratégie simple :

* clé : IP (ou autre si pertinent)
* stockage en mémoire
* compteur de tentatives
* fenêtre de temps
* blocage temporaire

Exemple attendu :

* X tentatives en Y minutes → blocage Z minutes

---

### 4. Comportement attendu

Décrire précisément :

#### a) cas nominal

* login OK

#### b) échec

* compteur incrémenté

#### c) dépassement

* blocage
* réponse utilisateur

#### d) reset

* quand et comment

---

### 5. Format de réponse

Définir :

* comportement côté UI (`/login`)
* message d’erreur
* comportement API si besoin

⚠️ Important :

* rester cohérent avec l’existant
* ne pas casser le flow actuel

---

### 6. Impacts techniques

Identifier :

* impact sur session
* impact sur logs
* impact sur tests
* impact sur architecture

---

### 7. Risques et pièges

Identifier les erreurs à éviter :

* stockage non thread-safe
* fuite mémoire
* blocage global au lieu de par IP
* contournement facile
* sur-complexité

---

### 8. Découpage du lot

Proposer un découpage en sous-étapes :

* implémentation cœur
* intégration
* tests
