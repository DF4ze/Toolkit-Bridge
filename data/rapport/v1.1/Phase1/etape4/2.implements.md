## 🎯 Objectif du lot

Ajouter un **rate limiting simple, local et robuste** sur le `POST /login` admin afin de limiter les tentatives de brute force.

---

## ✅ Stratégie imposée

L’implémentation doit suivre exactement cette stratégie :

* point d’intégration dans **`LoginController`**
* ajout d’un **service dédié léger** de rate limiting en mémoire
* clé de limitation : **`request.getRemoteAddr()` uniquement**
* politique :

    * **5 échecs**
    * dans une fenêtre de **10 minutes**
    * puis blocage de **15 minutes**
* en cas de succès :

    * reset immédiat de l’état associé à l’IP
* en cas de blocage :

    * rejet immédiat avant tentative d’authentification
    * retour au flow habituel `redirect:/login`
    * avec message flash :

        * `Too many login attempts. Please retry in a few minutes.`

---

## 🔒 Contraintes STRICTES

### Ce que tu dois faire

* rester dans un design **minimal**
* ajouter un composant technique localisé
* garder le flow actuel du login
* rendre l’ensemble facilement testable

### Ce que tu ne dois PAS faire

* ne pas utiliser `X-Forwarded-For`
* ne pas ajouter de dépendance externe
* ne pas utiliser Redis / Bucket4j / cache externe
* ne pas ajouter de filtre HTTP
* ne pas ajouter d’interceptor MVC
* ne pas modifier `AdminAuthenticationService`
* ne pas changer le contrat d’authentification actuel
* ne pas introduire de scheduler dédié
* ne pas sur-architecturer
* ne pas élargir à d’autres endpoints
* ne pas ajouter de logique API spécifique
* ne pas faire de calcul de temps restant pour l’utilisateur

## 🧩 Implémentation attendue

### 1. Service dédié de rate limiting

Créer un service léger, thread-safe, en mémoire.

Responsabilités attendues :

* savoir si une IP est actuellement bloquée
* enregistrer un échec
* réinitialiser l’état sur succès
* gérer la fenêtre temporelle
* gérer le blocage temporaire
* effectuer une purge opportuniste simple des états expirés

Contraintes techniques :

* stockage en mémoire uniquement
* thread-safe
* pas de scheduler
* pas de persistance

---

### 2. Intégration dans `LoginController`

Dans le `POST /login` :

#### Avant l’authentification

* récupérer l’IP via `request.getRemoteAddr()`
* vérifier si elle est bloquée
* si oui :

    * ne pas appeler `adminAuthenticationService.authenticate(...)`
    * ajouter le message flash :

        * `Too many login attempts. Please retry in a few minutes.`
    * rediriger vers `/login`

#### Après tentative d’authentification

* si succès :

    * reset du rate limiting pour cette IP
    * comportement existant inchangé
* si échec :

    * enregistrer l’échec pour cette IP
    * comportement existant inchangé tant que le seuil n’est pas dépassé

---

### 3. Politique fonctionnelle exacte

Appliquer exactement :

* seuil : **5 échecs**
* fenêtre : **10 minutes**
* blocage : **15 minutes**

Interprétation attendue :

* au 5e échec dans la fenêtre, l’IP passe en blocage
* toute tentative ultérieure pendant le blocage est refusée immédiatement

---

### 4. Logs

* ne pas introduire de logs détaillés inutiles
* si tu ajoutes un log, il doit être minimal et non sensible
* ne loggue jamais le token saisi

## 🧪 Tests attendus

### A. Tests unitaires du service de rate limiting

Vérifier au minimum :

* pas de blocage au début
* blocage après 5 échecs dans la fenêtre
* expiration du blocage
* reset sur succès
* purge opportuniste correcte

### B. Tests du contrôleur login

Compléter `LoginControllerTest` pour couvrir :

* login réussi inchangé
* login échoué sous le seuil inchangé
* IP bloquée => redirect `/login` + message de rate limiting
* succès après échecs => reset
* blocage => `authenticate(...)` non appelé

⚠️ Les tests doivent rester simples et ciblés.
